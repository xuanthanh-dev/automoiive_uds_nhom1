Hệ sinh thái ECU trong xe hơi

Một chiếc xe hiện đại có hơn 100 ECUs kết nối với nhau qua hệ thống Gateway tổng. ECU chúng ta xây dựng đóng vai trò là một Diagnostic Server kết nối qua cổng OBD-II.

  • Lưu trữ lỗi (DTC - Diagnostic Trouble Codes).

Xe hơi hiện đại: Siêu máy tính di động

Một chiếc xe ô tô hiện đại không còn chỉ là cơ khí thuần túy. Nó được định nghĩa bởi phần mềm (Software-Defined Vehicle - SDV).

ECU (Electronic Control Unit) là gì?

Phần cứng (Hardware)

  • MCU (Microcontroller): STM32, Aurix TC3xx, RH850...
  • Power Supply: Cung cấp nguồn ổn định (thường là 12V/24V hạ xuống 5V/3.3V).
  • Transceiver: Chuyển đổi tín hiệu logic sang tín hiệu đường truyền (ví dụ: TJA1050 cho CAN).
  • I/O Circuitry: Đọc cảm biến (ADC) và điều khiển cơ cấu chấp hành (PWM, Relays).

Phần mềm (Firmware)

  • Application Layer: Xử lý logic nghiệp vụ (ví dụ: Thuật toán chẩn đoán UDS).
  • Middleware / Services: ISO-TP, UDS stack, RTOS.
  • MCAL (Microcontroller Abstraction Layer): Điều khiển ngoại vi phần cứng (CAN Driver, GPIO Driver).
  • Bootloader: Cho phép cập nhật phần mềm từ xa (FOTA) qua mạng CAN/Ethernet.

Tầm quan trọng của Hệ thống Chẩn đoán xe (Diagnostics)

Tại sao xe hơi cần hệ thống chẩn đoán? Khi xe chạy trên đường, bất kỳ lỗi phần cứng hay phần mềm nào xảy ra đều phải được ghi nhận ngay lập tức để bảo vệ an toàn cho người lái.

Phát hiện & Lưu lỗi (DTC)

ECU liên tục giám sát các cảm biến. Nếu phát hiện ngắn mạch, hở mạch hoặc lỗi logic, nó sẽ lưu lại Diagnostic Trouble Code (DTC) vào bộ nhớ EEPROM/Flash.

Hỗ trợ sửa chữa bảo dưỡng

Kỹ thuật viên tại gara cắm thiết bị quét (OBD Dongle) vào cổng OBD-II của xe để đọc lỗi, xem thông số động cơ thời gian thực và xác định chính xác bộ phận bị hỏng.

Flash & Reset ECU

Hệ thống chẩn đoán cho phép các kỹ sư phần mềm cập nhật firmware mới cho ECU, hiệu chỉnh (Calibrate) các tham số hoạt động mà không cần tháo rời phần cứng.

Cách thức làm việc trong dự án Automotive

Dự án Automotive đòi hỏi độ tin cậy cực kỳ cao. Vì vậy, quy trình phát triển tuân thủ nghiêm ngặt mô hình V-Model và tiêu chuẩn chất lượng ASPICE.

  • Requirements: Mọi tính năng phải bắt nguồn từ Requirement rõ ràng, không code tùy tiện.
  • Traceability: Code phải tương ứng với thiết kế, và thiết kế phải tương ứng với Requirement.

Cấu trúc Thư mục Dự án nhúng chuẩn (File Management)

Để dự án có thể mở rộng và nhiều người cùng làm việc mà không bị xung đột, cấu trúc thư mục source code phải được module hóa rõ ràng:

/project_root
├── /Core (Mã nguồn chính từ CubeMX)
├── /Drivers (Thư viện STM32 HAL & CMSIS)
├── /ECU_Services (Nơi lưu code UDS, ISO-TP)
│ ├── /ISO_TP (Tầng truyền tải)
│ └── /UDS (Tầng ứng dụng chẩn đoán)
└── /App (Logic điều khiển nghiệp vụ)

Quy tắc quản lý file cốt lõi:

  • Tách biệt Layer: File driver không được gọi trực tiếp hàm của tầng ứng dụng.
  • Tên file rõ ràng: Đặt tên file theo module, ví dụ: uds_service_0x22.c, iso_tp_core.c.
  • File Header tự lập: Mỗi file .h phải có header guard (#ifndef ... #define) để tránh include lặp.

Tại sao dự án nhúng cần Git?

Nhiều sinh viên quen với việc nén file zip code gửi qua Zalo/Drive. Cách làm này phá hủy hoàn toàn tính chuyên nghiệp của một kỹ sư.

  • Đồng bộ mã nguồn: Nhiều người cùng code một dự án, tự động ghép (merge) code không lo bị đè đè đè.
  • Quản lý lịch sử: Biết ai sửa dòng code nào, sửa lúc nào, vì sao sửa.
  • Khôi phục an toàn: Dễ dàng quay lại phiên bản cũ hoạt động ổn định nếu code mới bị lỗi.

100% các công ty Automotive Embedded (FPT, Bosch, VinFast) đều sử dụng Git làm công cụ quản lý mã nguồn mặc định.

Quy chuẩn thông điệp Commit (Conventional Commits)

Không viết commit vô nghĩa như "fix bug", "up code", "abc". Hãy dùng chuẩn quốc tế:

<type>(<scope>): <subject>
  • feat: Phát triển tính năng mới (ví dụ: feat(can): add filters)
  • fix: Sửa lỗi trong code (ví dụ: fix(uds): correct positive response SID)
  • docs: Cập nhật tài liệu, comment (ví dụ: docs(readme): update build guide)
  • refactor: Tối ưu cấu trúc code, không đổi logic (ví dụ: refactor(uds): optimize state machine)
  • style: Sửa format code, căn lề, khoảng trắng (ví dụ: style(can): format code)

Cấu hình Clock & GPIO trong STM32CubeMX

Quy trình cấu hình vi điều khiển chuẩn xác:

  • Cấu hình bộ dao động (RCC): Chọn Crystal/Ceramic Resonator (HSE) ngoài để đảm bảo tần số Clock của bộ điều khiển CAN đạt độ chính xác cao nhất (không dùng bộ dao động RC nội của chip vì dễ bị trôi tần số theo nhiệt độ).
  • Cấu hình Clock Tree: Thiết lập tần số SYSCLK mong muốn (ví dụ: 72MHz hoặc 168MHz).
  • Cấu hình GPIO điều khiển LED: Thiết lập chân GPIO Output để điều khiển LED báo trạng thái của ECU.

Chú ý cực kỳ quan trọng:

Khi sinh code từ STM32CubeMX, toàn bộ code tự viết của bạn phải nằm trong các vùng được đánh dấu sẵn:
/* USER CODE BEGIN ... */ và
/* USER CODE END ... */.
Nếu viết ngoài vùng này, code sẽ bị xóa sạch khi bạn cấu hình lại CubeMX và nhấn Generate Code!

Bước 3: Viết mã nguồn điều khiển LED (HAL)

Mở file Core/Src/main.c, tìm đến vòng lặp while(1) và viết code nhấp nháy LED:

/* USER CODE BEGIN WHILE */
while (1)
{
    /* Tải trạng thái chân GPIO điều khiển LED */
    HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);

    /* Tạo độ trễ 500ms */
    HAL_Delay(500);

    /* USER CODE END WHILE */
    /* USER CODE BEGIN 3 */
}
/* USER CODE END 3 */

Toolchain & STM32 Bring-up

STM32 & CAN Transceiver

Môi trường phát triển và ghép nối phần cứng cốt lõi:

  • Cấu hình Clock: Đảm bảo tần số CAN ổn định, chống trôi lệch Baudrate do nhiệt độ.

Đặc tính vật lý vi sai của CAN Bus

CAN Bus sử dụng hai đường dây xoắn đôi CAN_High và CAN_Low để truyền tải tín hiệu vi sai.

  • Trạng thái Tĩnh (Recessive - logic 1): CAN_H = 2.5V, CAN_L = 2.5V. Hiệu điện thế vi sai Vdiff = 0V.
  • Trạng thái Động (Dominant - logic 0): CAN_H = 3.5V, CAN_L = 1.5V. Hiệu điện thế vi sai Vdiff = 2V.
  • Điện trở đầu cuối 120 Ohm: Phải được đấu ở 2 đầu xa nhất của mạng Bus để triệt tiêu sóng phản xạ tín hiệu.

CAN Transceiver & Vai trò chuyển đổi tín hiệu

Cơ chế Phân xử Bus (Arbitration) tránh va chạm

Trên mạng CAN Bus, khi nhiều ECU đồng thời muốn gửi tin, cơ chế **Phân xử không phá hủy** sẽ bảo vệ tính toàn vẹn của đường truyền.

  • Nguyên tắc ghi đè: Trạng thái Dominant (logic 0) luôn ghi đè trạng thái Recessive (logic 1).
  • So sánh từng bit ID: Các ECU đồng thời phát ID của mình lên Bus. ECU nào phát bit Recessive (1) trong khi phát hiện Bus bị kéo xuống Dominant (0) bởi ECU khác sẽ lập tức đầu hàng, chuyển sang chế độ nhận.
  • Độ ưu tiên ID: ID có giá trị số càng nhỏ thì độ ưu tiên càng cao (chứa nhiều bit 0 Dominant hơn ở đầu).

Không mất mát dữ liệu

ECU thua cuộc phân xử sẽ tự động chờ đến khi mạng Bus rảnh để thử phát lại bản tin.
Quá trình này diễn ra hoàn toàn bằng phần cứng tích hợp sẵn trong chip điều khiển CAN của MCU, không cần viết code xử lý.

Cấu hình Baudrate của CAN trên STM32

Để tất cả các ECU trong mạng giao tiếp được với nhau, tần số truyền nhận (Baudrate) phải cấu hình hoàn toàn trùng khớp (ví dụ: 500 kbps cho chẩn đoán).

Thời gian truyền 1 Bit được chia làm các phân đoạn:

  • Sync_Seg: Đồng bộ xung nhịp (thường mặc định là 1 Time Quanta).
  • Bit Segment 1 (BS1): Bao gồm Prop_Seg và Phase_Seg1 để bù đắp trễ đường truyền đường dây.
  • Bit Segment 2 (BS2): Phase_Seg2 giúp xác định thời điểm lấy mẫu chính xác.

Công thức: Baudrate = CAN_Clock / (Prescaler * (1 + BS1 + BS2))

Ví dụ cấu hình (Clock = 42MHz):

Để đạt tốc độ truyền chẩn đoán chuẩn 500 kbps:
- Prescaler = 6
- BS1 = 11 Tq
- BS2 = 2 Tq
- 1 + BS1 + BS2 = 14 Tq
- Baudrate = 42MHz / (6 * 14) = 500 kbps.

Bộ lọc CAN (CAN Filters) - Tiết kiệm tài nguyên CPU

Trên mạng xe hơi, hàng trăm ECU liên tục phát các bản tin lên bus. Nếu CPU của STM32 phải nhảy vào xử lý ngắt nhận cho mọi gói tin thì sẽ bị quá tải ngay lập tức.

  • Chế độ Mask Mode: Định nghĩa một bộ "mặt nạ" giúp lọc một nhóm dải ID cùng lúc (phù hợp nhận diện nhiều ECU liên quan).

Tại sao cần giao thức ISO-TP?

Một gói tin CAN Bus truyền thống (CAN 2.0B) chỉ có thể mang tối đa 8 Bytes dữ liệu.

Tuy nhiên, các dịch vụ chẩn đoán UDS thường truyền nhận các gói tin có dung lượng lớn hơn nhiều (Ví dụ: Đọc chuỗi số khung xe VIN dài 17 bytes, truyền file Firmware nâng cấp phần mềm lên tới vài chục Kilobytes).

Giải pháp: Tiêu chuẩn ISO-TP (ISO 15765-2)

Đóng vai trò là tầng vận tải, chịu trách nhiệm phân tách gói tin lớn thành các Frame CAN nhỏ để gửi đi, và ghép nối các Frame CAN nhỏ nhận được thành gói tin hoàn chỉnh ở đầu nhận.

Phân mảnh gói tin

Cho phép truyền tải chiều dài gói tin lý thuyết lên tới tối đa 4095 Bytes qua đường truyền CAN vật lý.

Bốn loại Frame chính trong cấu trúc ISO-TP

ISO-TP định nghĩa Byte đầu tiên trong vùng dữ liệu 8-byte của CAN Frame làm mã định dạng Frame:

1. Single Frame (SF) - Type 0

Dùng khi toàn bộ gói tin chẩn đoán nhỏ hơn hoặc bằng 7 Bytes. Truyền trực tiếp trong 1 Frame duy nhất.

[Byte 0: 0x0_ + Length] [Byte 1..7: Data]

2. First Frame (FF) - Type 1

Bản tin khởi đầu cho chuỗi truyền gói dữ liệu lớn. Khai báo tổng chiều dài gói chẩn đoán sắp truyền.

[Byte 0: 0x1_] [Byte 1: Total Length] [Byte 2..7: Data]

3. Flow Control (FC) - Type 3

Phát từ đầu nhận gửi ngược lại đầu truyền để điều phối tốc độ, khai báo kích thước bộ đệm sẵn sàng nhận.

[Byte 0: 0x30 (CTS)] [Byte 1: Block Size] [Byte 2: STmin]

4. Consecutive Frame (CF) - Type 2

Các bản tin nối tiếp chứa phần dữ liệu còn lại của gói tin. Đánh số thứ tự tăng dần (Sequence Number) từ 1 đến 15.

[Byte 0: 0x2_ + SeqNum] [Byte 1..7: Remaining Data]
© Copyright FPT fpt.auto | Slide 42
Sơ đồ hoạt động truyền nhận Multi-frame ISO-TP

Thứ tự bắt tay truyền tin:

  1. Sender gửi bản tin khởi đầu First Frame (FF) báo muốn gửi 20 bytes.
  2. Receiver nhận được FF, gửi lại bản tin điều phối Flow Control (FC) xác nhận sẵn sàng nhận (CTS = 0), yêu cầu truyền liên tiếp (Block Size = 0) và khoảng thời gian trễ giữa các gói STmin = 10ms.
  3. Sender bắt đầu gửi chuỗi bản tin nối tiếp Consecutive Frame (CF) chứa phần dữ liệu còn lại cho đến khi đủ 20 bytes.
Sender --[ FF: Length=20, Data... ]--> Receiver
Sender <--[ FC: CTS=0, BS=0, STmin=10ms ]-- Receiver
Sender --[ CF: Seq=1, Data... ]--> Receiver
Sender --[ CF: Seq=2, Data... ]--> Receiver
Sender --[ CF: Seq=3, Data... ]--> Receiver

UDS (Unified Diagnostic Services) là gì?

UDS (ISO 14229) là tiêu chuẩn giao thức chẩn đoán thống nhất toàn cầu được hầu hết các hãng xe lớn trên thế giới sử dụng.

  • Mô hình Client-Server: Thiết bị chẩn đoán (PC, máy quét lỗi) là Client gửi yêu cầu (Request) -> ECU trên xe đóng vai trò là Server phản hồi kết quả (Response).
  • Định dạng Service ID (SID): Mỗi dịch vụ chẩn đoán được đại diện bằng một mã số Hex 1 byte duy nhất.

Client / Server

Hội thoại hỏi-đáp liên tục giúp kiểm soát toàn bộ vòng đời hoạt động của hệ thống phần cứng trên xe.

Cấu trúc Bản tin UDS Request & Response

Một phiên giao tiếp chẩn đoán UDS luôn diễn ra theo luồng định dạng dữ liệu chuẩn:

1. Diagnostic Request (Client -> ECU Server):
[Byte 0: SID (1 Byte)] [Byte 1: Sub-function / Parameter] [Byte 2..N: Data Parameters]
2. Positive Response (ECU Server xử lý thành công):
[Byte 0: SID + 0x40] [Byte 1: Sub-function / Echo Parameter] [Byte 2..N: Response Data]
3. Negative Response (ECU Server phát hiện yêu cầu lỗi hoặc từ chối):
[Byte 0: 0x7F (Mã cố định NRC)] [Byte 1: SID bị từ chối] [Byte 2: NRC (Negative Response Code)]

Dịch vụ 0x10 - Diagnostic Session Control

Dịch vụ chuyển đổi phiên chẩn đoán, cho phép mở rộng các quyền truy cập vào các tính năng bảo mật cao hơn của ECU.

Ba loại Session chính được định nghĩa trong dự án:

  • Default Session (0x01): Trạng thái khởi tạo mặc định khi ECU khởi động. Chỉ cho phép đọc các dữ liệu cơ bản không nhạy cảm.
  • Programming Session (0x02): Phiên làm việc dành riêng cho tác vụ ghi đè phần mềm, flash bootloader.
  • Extended Session (0x03): Phiên chẩn đoán mở rộng. Cho phép truy cập các cảm biến chuyên sâu, điều khiển cơ cấu chấp hành trực tiếp.

Dịch vụ 0x27 - Security Access (Seed & Key)

Cơ chế bảo mật Seed & Key giúp ECU xác thực chính xác thiết bị kết nối có phải công cụ chính hãng hay không:

Các bước bắt tay bảo mật:

  1. Client gửi yêu cầu lấy Seed: Gửi dịch vụ 0x27 với sub-function là 0x01.
  2. ECU sinh chuỗi ngẫu nhiên (Seed): ECU trả về một dãy số ngẫu nhiên ngầm sinh (ví dụ: 4 bytes).
  3. Tính toán khóa (Key): Cả Client và ECU độc lập chạy một thuật toán mã hóa bí mật (ví dụ: AES, XOR...) trên chuỗi Seed để sinh ra Key.
  4. Client gửi Key: Gửi lại dịch vụ 0x27 với sub-function 0x02 kèm theo Key vừa tính.
  5. ECU đối chiếu: So khớp Key nhận được từ Client với Key tự tính. Nếu khớp, ECU sẽ mở khóa các dịch vụ bảo vệ.

CAN Controller vs CAN Transceiver

CAN Controller

CAN Controller là khối ngoại vi nằm trong MCU, ví dụ trong STM32. Khối này xử lý phần logic/protocol của CAN frame.

  • Đóng gói và giải mã CAN frame.
  • Quản lý Identifier, DLC, Data, ACK, CRC.
  • Thực hiện arbitration, error handling ở mức controller.
  • Cung cấp mailbox, FIFO, filter và interrupt cho firmware.
  • Làm việc với tín hiệu logic CAN_TX và CAN_RX.

CAN Transceiver

CAN Transceiver là chip/module phần cứng bên ngoài MCU. Nó chuyển đổi tín hiệu logic từ MCU sang tín hiệu vi sai vật lý trên bus.

  • Nhận TXD từ MCU và tạo tín hiệu CAN_H/CAN_L.
  • Đọc tín hiệu vi sai trên bus và xuất RXD về MCU.
  • Không xử lý UDS, DID, DTC hay application logic.
  • Cần cấp đúng điện áp theo module, ví dụ 3.3V hoặc 5V.
  • Là thành phần bắt buộc nếu muốn kết nối CAN vật lý thật.

Thông điệp chính: STM32 có CAN Controller, nhưng không thể nối trực tiếp vào CAN_H/CAN_L. Muốn giao tiếp trên bus CAN thật, luôn cần CAN Transceiver.

Những điểm sinh viên cần nhớ

  • Firmware không gửi trực tiếp CAN_H/CAN_L; firmware gửi CAN frame qua CAN peripheral.
  • CAN_TX/CAN_RX là tín hiệu logic giữa STM32 và transceiver.
  • CAN_H/CAN_L là tín hiệu vật lý vi sai giữa các node trên bus.
  • GND chung giữa các board/transceiver là điều kiện cần trong setup lab.
  • Termination 120Ω đặt ở hai đầu bus giúp giảm phản xạ tín hiệu.
  • Khi debug lỗi CAN, cần tách lỗi theo tầng: wiring → transceiver → CAN config → filter → callback → application.
